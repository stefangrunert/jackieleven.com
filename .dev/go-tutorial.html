1. What you will learn

This tutorial explains Go through the website you already know. With PHP and JavaScript experience, you do not need loops, HTTP and templates explained from scratch. The main new elements are Go’s types, a long-running server, and responsibility for shared state.

After reading, you should be able to start the server, follow a request through the code, test a small change, and explain why our Go version still resembles PHP in places. You need neither a Go framework nor systems-programming knowledge.

Reading path. For a first practical pass: start locally, understand the files, follow a request. The language chapters then explain the syntax you encountered. The exercises connect both.

The Go examples refer to the reviewed project revision 9795efc of 26 October 2026. Local operating scripts introduced afterwards and the architecture comparison are supplementary documentation. Excerpts labelled ‘Original’ come from that code. Shortened excerpts and additional learning examples are identified accordingly. The PHP version remains available in the tag php-before-go-migration. The planned ontology and search are not yet part of this Go server.

2. From a PHP request to a running Go program

In our previous PHP application, the web server accepted a request and had PHP execute the entry point. The program loaded its functions, selected a language and generated HTML. In conventional PHP-FPM operation, ordinary PHP variables are then rebuilt for the next request. FPM workers themselves may remain running, and OPcache can retain compiled PHP code.

Our Go application instead starts once and waits for HTTP requests. The process loads catalogues and templates, keeps them in memory and handles many requests through the same App. Only a restart rebuilds that application. This resembles a Node.js server more than a conventional PHP entry script, although execution and concurrency differ from the JavaScript event loop.

  1. Once per process: Start program → read configuration → load data → parse templates → open HTTP port.
  2. For each page request: Create request-local state → determine language and route → prepare data → render HTML.
  3. At shutdown: Stop accepting new connections → finish active requests within the deadline → exit.

Shared memory persists between requests. State belonging to one request must therefore not live in mutable global variables.

Go compiles source code into an executable before running it. Even go run compiles first; it merely hides the temporary build. The executable includes the required Go runtime, such as the scheduler and garbage collector. Go manages memory automatically but still requires files, HTTP response bodies and other resources to be closed.

Our release nevertheless contains more than a binary: JSON, templates, Markdown and assets remain external files. We do not use go:embed here. A server given only the binary without these contents cannot serve the complete website.

3. Local development: run, compile, restart

The persistent local setup on this MacBook

https://jackieleven.localhost/de/ has led to the Go application since 26 October 2026. Two independent services work together: MAMP accepts the HTTPS request and our long-running Go program generates the response. The former PHP application no longer renders pages for this local host.

  1. Local name: The existing entries for jackieleven.localhost resolve to this MacBook.
  2. MAMP Apache, port 443: uses the existing local certificate and accepts HTTPS.
  3. Reverse proxy: forwards the request to http://127.0.0.1:8080 and preserves the original hostname.
  4. Go login service: loads the application from /Users/stefan/www/jackieleven and sends its response back through Apache.

The browser sees the HTTPS address without a port. The internal Go port is restricted to loopback. The exercise server on 8081 is a separate instance.

MAMP is the HTTPS entry point here; the Go process requires neither PHP-FPM nor a PHP interpreter. MAMP can still serve other projects. If MAMP is stopped, this HTTPS address fails even if Go keeps running on 8080. Conversely, Apache cannot return an application response when the Go service is stopped.

What ‘permanent’ means here

A macOS LaunchAgent named com.stefan.jackieleven.go starts Go at login, independently of a terminal or this chat. RunAtLoad starts the program when the service loads; KeepAlive restarts it after the process exits. The installed plist is at ~/Library/LaunchAgents/com.stefan.jackieleven.go.plist.

The user service ends at logout. The MacBook serves no requests while asleep. This is a persistently configured local development environment, not an always-accessible server. Automatic restart was tested with a deliberate SIGTERM; no full Mac restart was performed for that check.

Daily operating commands

cd /Users/stefan/www/jackieleven
ops/go-local.sh restart  # Rebuild Go and restart the service
ops/go-local.sh reload   # Restart and reload data without rebuilding
ops/go-local.sh status   # launchd state and process information
ops/go-local.sh logs     # Last 60 entries in the error/startup log
ops/go-local.sh stop     # Unload for the current login session
ops/go-local.sh start    # Enable and load

restart first builds a new binary and replaces the old file only after successful compilation. A compiler error leaves the existing service running. The service is then unloaded and reloaded. reload also performs a real process restart, without a build: JSON, templates and columns are read again. Neither command enables a file watcher or promises uninterrupted operation.

stop unloads the service so that KeepAlive does not immediately restart it during this login session. At the next login, the installed plist loads again. For permanent shutdown, the additional launchctl disable steps are in GO-LOKAL.md. ops/go-local.sh install generates the plist from current local paths; it is a setup command, not a required daily step.

5. Reading Go: variables, functions and control flow

We begin with an actual line from the entry point:

:= declares a variable inside a function and infers its type from the expression. Here the result is *string because flag.String returns a pointer to a string. A subsequent = assigns a new value to an existing variable. Its type remains fixed; listen = 42 does not compile.

Go places the type after the name: name string. if needs no parentheses around the condition, but braces around the block. for covers counting loops, collection iteration and loops like while. range returns index and value for a slice. _ discards an unneeded value, as in for _, name := range names.

A condition must be Boolean. if count and if lang are invalid; write if count != 0 or if lang != "" instead. The project’s function truth is custom PHP compatibility, not a Go language feature.

func defines a function; header string is its parameter, and the final string is its return type. The simplified example above shows only the form. Our actual function also handles weights in the Accept-Language header.

The three dots in a signature such as args ...any mean a variable number of arguments, received inside the function as a slice. At the call site, args... passes an existing slice’s elements as individual arguments. Both appear in our URL and template helpers; the idea resembles variadic arguments or spread in PHP and JavaScript.

Unused local variables and imports are compiler errors. Formatting is handled by gofmt. This initially feels strict but makes much code checkable before opening a browser. Basic rules are in the language specification; the constructs explained here are enough to begin reading our application.

6. Structs, methods and pointers

Instead of an arbitrarily extensible configuration array, the server uses a named type with fixed fields:

struct groups fields. site.Config{Root: *root, BasePath: *basePath} creates a value and sets named fields. Unspecified fields receive their zero values. A constructor called __construct does not exist automatically. Our function New validates configuration and builds the app; its name is a convention.

The first signature returns two values: a pointer to an App and an error value. The second is a method of *App. The part (a *App) is called the receiver; inside the method, a is the equivalent of an explicitly named $this. Go has methods and interfaces, but no class inheritance in the PHP sense.

What do * and &?

&config takes the address. In a type declaration, *Config means ‘pointer to Config’; as an expression, *p reads the value at that address. Go dereferences automatically for field access. There is no ordinary pointer arithmetic as in C.

Go passes arguments by value. Passing a struct copies that struct value. Passing a pointer copies the pointer value; both pointers can then access the same structure. &App{...} in New creates our app and returns its address. You do not need to dispose of the structure manually with free.

An initial uppercase letter exports a name from the package: Config, New and ServeHTTP are accessible from outside. request, loadData and root are package-internal. This also applies to struct fields: template and JSON libraries can read exported fields normally.

7. Maps, slices, any and our content data

PHP arrays cover lists and ordered key-value mappings. Go separates these: a []string is a slice of strings; a map[string]string maps string keys to string values. A Go array such as [2]string has a fixed length that is part of its type.

The second return value from map access distinguishes a missing entry from an existing empty string. A nil map can be read but not written. To write to one, create it with map[string]string{} or make(map[string]string). A nil slice, however, can be extended using append.

Assigning a map does not copy all entries. A slice may also share its underlying memory with other slices. This differs from the usual copy-on-write expectations for PHP arrays. cloneMap copies only the top map level in our project; nested maps and slices remain shared. The official slice explanation details this memory model.

Strings, bytes and Unicode

Go strings are immutable byte sequences, usually UTF-8 in our texts. len(s) counts bytes; s[i] returns one byte. range over a string instead decodes Unicode code points, called rune in Go. For "ü", the byte count is 2 and the code-point count is 1. The form therefore uses utf8.RuneCountInString for length rules. Even code points are not always equivalent to visibly perceived characters, for example with combining accents.

Why our code uses M so often

M is an alias for map[string]any because of the equals sign, not a distinct new type. any names the empty interface: a value of this type can contain different concrete types. It resembles PHP’s mixed. It does not make Go generally dynamically typed; before type-specific operations, you must establish the concrete type.

The form value.(string) is a type assertion, not string conversion. With text, ok := ... you get a result you can check; without ok, an incorrect assumption can cause a panic.

loadData reads JSON files using os.ReadFile and json.Unmarshal. When the target type is any, JSON objects become maps, arrays become []any and numbers default to float64. This explains our conversion helpers such as str and num. Reference: json.Unmarshal.

The backtick strings are struct tags. Here they tell the JSON package the field names. The field Title would then be checked by the compiler; a typo in record["titel"] within an open map is discovered only at runtime or in a test. 8. Errors are return values; defer cleans up

Loading a file may fail in an expected way. Go typically uses an additional return value for this:

b contains bytes on success, while err is nil. On error, the function returns early. This is not try/catch: the caller receives the error as an ordinary value and decides how to handle it. The type error is an interface with the method Error() string.

Our loadData adds the filename for invalid JSON through fmt.Errorf("%s: %w", name, err). %w preserves the underlying error for further inspection. If site.New fails, main aborts startup with log.Fatal. For a rendering error during a request, renderError instead logs the error and responds with HTTP 500. Stopping the whole site over a failed response would be a different decision.

Arrange resource cleanup immediately after opening

defer executes the specified call when the surrounding function exits, including after a later return. Multiple deferred calls run in reverse order. This resembles cleanup in finally, but is scoped to the function. In a long loop, defer therefore retains resources until the function ends.

panic and recover exist, but do not replace ordinary validation and I/O errors. Nor does defer guarantee cleanup after abrupt process termination; log.Fatal exits through os.Exit without running pending defers. See Go: Defer, Panic, and Recover.

9. What actually happens at startup

The file main.go uses package main and contains func main(). This is where the executable begins. The first part of actual startup is:

flag.Parse() reads the arguments following the program name. The previously created pointers root, basePath and trust yield their values through *. ContactConfigFromEnv() reads form configuration from the process environment. The Go code does not execute app/config.local.php; a .env file is not automatically loaded either.

site.New first normalises the optional preview path and content root. It loads JSON data and columns, creates the contact component and configures the asset file server. It then reads all .gohtml files and parses them using html/template. Any error is returned to main. Otherwise a fully prepared *App is ready.

The function HTTPServer places this app in an http.Server and sets time limits: five seconds for request headers, 15 for reading, 45 for writing and 60 for idle keep-alive connections. 10. How our app becomes an HTTP handler

Go interfaces describe required methods. The HTTP server requires a handler of this form:

Our method func (a *App) ServeHTTP(...) satisfies exactly this requirement. No implements Handler is needed. Matching the method signature is enough. Therefore HTTPServer(addr string, handler http.Handler) accepts our *App without knowing its concrete type.

r *http.Request provides method, address, headers and body. Instead of reading $_SERVER and $_POST, the handler works with this object. w http.ResponseWriter is the interface for writing the response: set headers, send status, write the body. An interface value can refer to a concrete implementation; in tests, for example, a response recorder.

Order matters: after the first body write, changing status is usually too late; without an explicit WriteHeader, 200 is assumed. Our page first renders into buffers and writes the actual response only after rendering succeeds. This serves the same purpose as a PHP output buffer.

http.HandlerFunc turns a function with the appropriate signature into a handler. The mount code uses it in http.HandlerFunc(a.serveHTTP). Routing is handled by our own serve method; we use neither a framework nor a ServeMux. Reference: net/http.Handler.

11. Following a request: from URL to HTML

Consider GET /de/diskografie. You can follow these steps directly in the code. The browser still receives server-rendered HTML; Go does not replace browser JavaScript here.

  1. App.ServeHTTP: first checks a possible mount such as /jackieleven. On the main domain, the mount is empty.
  2. App.serveHTTP: recognises that this is not an asset request. It creates a separate request and clones the prepared templates.
  3. request.serve: splits the path. de becomes the language; translated route entries identify diskografie as the page.
  4. request.page: receives the view name, title, navigation state and status 200.
  5. render → viewData: retrieves releases, groups them by year and provides sources.
  6. diskografie.gohtml: generates the catalogue. Then layout.gohtml wraps the content with the head, navigation, metadata and script references.
  7. HTTP response and browser: Go sends headers and HTML. The browser loads CSS, images and JavaScript and runs the interactive features.

The data preparation for the discography is surprisingly small:

c.releases() retrieves the release list. The anonymous function func(p any) string { ... } calculates each record’s grouping key, equivalent to a callback in PHP or JavaScript. group preserves order through []Pair; ordinary map iteration in Go guarantees no fixed order.

Where does discography filtering happen?

The overview page contains the catalogue. The script assets/js/diskografie.js shows or hides entries by project and format and manages the URL and browser history. Go also handles filter context for detail pages, return links and neighbouring records. Looking in the Go handler for the entire interactive filter therefore means looking in the wrong place.

For /de/diskografie/1975-control, routing takes the detail branch: releaseContext reads query context; release finds the record; page renders the view platte. An unknown ID returns the custom 404 page. The old ID 1973-control redirects to the current one. This behaviour is part of the migration contract.

When changing timeline stations, the browser can use ?fragment=1 to request only the stage fragment. Go generates that HTML too; JavaScript inserts it into the existing page. Full page and fragment are two response forms of the same application.

12. Templates, functions and safe HTML

Our PHP version used extract, ob_start and require to execute a view with local variables. The Go version instead parses a restricted template language. Files ending in .gohtml do not execute arbitrary Go code.

The dot . denotes the supplied data, here a map. $platte is a local template variable; := introduces it. get and asset are functions registered in our FuncMap. if, range and end belong to the template language. Inside a range block, the dot may refer to the current element; named variables help keep track.

The many parentheses and helpers in our real templates reflect a cautious transfer of PHP output. New Go templates could use fixed view models for simpler expressions such as {{.Title}}. Both are possible; the existing style is not mandatory for all Go websites.

Why clone per request?

The functions t, url and sprache depend on the current language and route. c.functions() creates method values and closures that use the specific request c. At startup, a dummy request supplies function names for parsing. For a real request, the unused base is cloned and function bindings replaced with those of the current request. Two visitors therefore do not share a mutable language function.

This is our implementation’s solution, not a general requirement of html/template. A purely data-driven, immutable template set can also run concurrently after preparation. Our request-dependent function bindings explain the extra clone.

Escaping is part of rendering

html/template escapes ordinary values for their HTML context. A title such as <script>…</script> is output as text. template.HTML explicitly marks HTML as trusted. This conversion sanitises nothing; it bypasses normal escaping for that value.

In our code, such HTML comes from rendered project partials or the Markdown reader, which first escapes text and emits only limited tags. attrs allows a narrow set of predefined attributes before returning template.HTMLAttr. User input must not simply be converted to these types. The boundary is described in html/template: security model.

13. Concurrent requests and shared state

A Go server can execute several handlers concurrently. The HTTP library arranges concurrency; we do not start a new goroutine inside every handler. A goroutine is an execution flow managed by the Go runtime. Several may alternate or run genuinely in parallel on multiple CPU cores. A blocking network call therefore need not halt the entire website.

The two central structures show how we separate data lifetimes:

App.data is read-only within the application after loading. request.lang, route, slug and title belong to an individual request. German and English requests receive different request values but refer to the same catalogues. Go does not enforce their immutability; the code must respect that rule.

The old PHP helper sprache() could keep its current value in a static local variable because that state remained within the conventional request lifecycle. An equivalent mutable package value in Go could be overwritten between German and English responses. The test TestRequestLanguageIsIsolated therefore makes 48 concurrent requests and checks language and canonical URLs.

If shared data later becomes mutable, we need a synchronisation design, such as mutex protection or atomic replacement of a fully built data state. ‘Only one process is running’ does not guarantee freedom from concurrent access. go test -race can detect memory accesses lacking proper synchronisation along executed test paths; a passing run does not prove every possible execution. 14. The form: state, concurrency and external services

The contact form cannot remain read-only: it changes sessions, CSRF tokens and delivery status. PHP supplied session infrastructure; Go does not automatically provide our application with $_SESSION. We implemented this state explicitly.

Contact.Handle uses the cookie jackie_contact to open or create a session file. syscall.Flock locks it for the entire processing operation, including validation and delivery. A second request from the same session must wait. This matters when two tabs submit the same token almost simultaneously. defer closeLocked(f) releases the lock when the function exits.

The session stores form tokens, timestamps and replay identifiers. Message text and email address are not stored in plaintext in these session files. IP limits have separate locked state files. A Go mutex would coordinate only within one process; file locking suits our file-based state and local cleanup.

  1. Open form: Open session, provide token, return HTML with private caching rules.
  2. Validate POST: Check body size, token and age, honeypot, cooldown, input fields and attempt limit.
  3. Verify Turnstile: Call the provider using the request context and a separate timeout.
  4. Prepare delivery: Persist an identifier for token and message content, then call Resend.
  5. Save success: Consume the token and redirect to the form page with HTTP 303.

If a delivery request ends with an uncertain outcome, retrying the same form content uses the same idempotency key. The provider can then recognise repeated requests. This is specific replay protection, not a universal exactly-once guarantee under every possible failure.

Functions can be passed as dependencies

Now, Verify and Send are fields holding function values. Without explicit values, NewContact uses the real clock and provider functions. Tests substitute controllable time and replacement functions. This lets us test an expired session without waiting two hours and simulate delivery failure without sending emails. It is dependency injection using ordinary Go values, without a container or framework.

A limitation of the current implementation: syscall.Flock is tied to the Unix platforms used here. macOS and Linux are intended targets; a Windows build is not automatically supported, although Go itself supports Windows.

15. Context, goroutines and graceful shutdown

A context.Context carries cancellation signals and deadlines through function calls. r.Context() belongs to the incoming HTTP request. The form passes it to provider functions. Turnstile verification adds a further time limit:

http.NewRequestWithContext binds the outgoing HTTP request to this context. On cancellation or timeout, the HTTP library can stop its work. A context does not interrupt arbitrary code automatically: each function must honour it. In particular, it does not automatically make the blocking file lock used here cancellable. See context.

In the entry point, a separate goroutine watches for process termination. This original excerpt contains almost all the language features required:

signal.NotifyContext connects Ctrl+C or SIGTERM to a context. go func() { ... }() starts an anonymous function as a goroutine. It waits at <-ctx.Done() until the context signals cancellation, then calls Shutdown with a 30-second deadline.

make(chan struct{}) creates a channel for a signal without payload. close(shutdownDone) signals completion. After ListenAndServe ends, main waits for it using <-shutdownDone. Without this wait, main could exit and terminate the process while the shutdown goroutine was still running.

The systemd unit allows 35 seconds for stopping, slightly more than the internal shutdown deadline. This provides graceful shutdown within a deadline, not a promise that arbitrarily long requests always finish.

17. From local build to a release on Hetzner

Locally we build for macOS/arm64; production uses Linux/amd64. Go selects the target platform through GOOS and GOARCH. Our packaging tool handles this and also sets CGO_ENABLED=0; the application needs no linked C library.

The packaging command creates the binary, selected content, build.json and a SHA-256 manifest. Included files are explicitly listed in ops/go-release-files.json. .dev, local credentials and arbitrary research files are not automatically published this way. This command uploads nothing and starts no service on Hetzner.

  1. Browser → Cloudflare → nginx: Public access, TLS and upstream rules.
  2. nginx → Go: Forwarding to the locally bound port 127.0.0.1:18765.
  3. systemd: Starts and monitors Go, supplies configuration and limits permissions.
  4. Release directory: Contains the matching binary, data, templates and assets.

The launcher ops/run-go-release.sh resolves the link go-current exactly once and starts the program with this fixed -root. This prevents a running process from mixing old in-memory data with new files from another release after the link changes.

The unit jackieleven-go.service runs as user jackieleven. Production provider values come from /etc/jackieleven/go.env; contact state is stored at /var/lib/jackieleven-go/contact. The application trusts proxy headers only with -trust-proxy and a direct loopback peer. nginx must set these headers in a controlled way.

A new build does not replace a running process automatically. Switching versions consists of validating the package, creating a new release directory, changing the link and restarting. This simple procedure may cause a brief interruption; it is not a zero-downtime procedure. Detailed operations and rollback instructions are in GO-BETRIEB.md.

The preview at unpubli.sh/jackieleven uses its own process and -base-path /jackieleven. The mount affects local links, assets and cookie paths. Canonical URLs still point to the main domain; the preview remains noindex. This separation is our site’s deployment logic, not a built-in Go concept.

Four migration choices you should not learn as Go rules

Open catalogues. map[string]any avoids rebuilding all data schemas at once. Concrete structs would often make new domain rules more readable and checkable. Configuration, request and session structures already demonstrate this fixed typing.

PHP-like helpers. Names such as in_array, array_filter and coalesce in the FuncMap transfer existing behaviour. In particular, choose is an ordinary function call, not a short-circuiting ternary operator. Its arguments are evaluated before it selects a value. Conditional or expensive work belongs in a real if block.

Custom parsers. parseFormValues preserves existing rules for repeated form keys and array notation. This is not equivalent to an unexamined switch to url.Values.Get after standard parsing. Email validation and Markdown rendering also reproduce defined existing rules. A new project would need fresh justification for these choices.

Custom router and template clones. Both solve specific problems for this small site. Go does not prescribe this architecture. Later refactoring could separate routing, view models and domain data more clearly, while keeping existing comparisons passing.

Runtime claims also require precision: compilation and preloaded data change the cost model but do not establish any particular speed advantage. Our migration evidence primarily checks behaviour. A reliable performance claim requires measurements under comparable loads.

19. Go, Node.js and Java: the same website, different runtime models

Our website could have a similar structure in all three environments: HTTP entry point, router, content preparation, templates and contact component. Node.js and Java can also load catalogues at startup and return server-rendered HTML. Language choice determines neither monolith versus microservices nor SQL versus files versus search engine. The main difference is how the running process executes work and waits for I/O.

The comparison here uses a Node.js HTTP server and a Java web application on the JVM, for example with Spring Boot. These are possible comparison architectures; the repository contains no Node or Java ports. Framework choices are explicitly distinguished from language features.

The shared framework

  1. Startup: Read configuration, load catalogues, prepare templates and start HTTP handling.
  2. Request: Determine language and route, select data, generate HTML or call an external service.
  3. Operations: Monitor the process, retain state, deploy changes and restart in a controlled way.

Our local MAMP → backend → response chain could serve a Go, Node.js or Java process. Neither launchd nor systemd is tied to Go.

Node.js: an event loop is not one thread per request

In a typical Node server, one event-loop thread executes JavaScript for many requests. When a handler uses await to wait for an asynchronous network response, other code can continue. Depending on the operation, the operating system and internal workers support the work. This does not mean the entire Node process has only one thread. Node.js: event loop.

A Node version of our form might run await verifyTurnstile(...), followed by await sendMail(...). This is as readable step by step as the Go version. But async does not automatically make a long JavaScript calculation concurrent: if a handler synchronously builds a large index, the event loop remains occupied. Even await buildIndex() does not help if the function call performs all its CPU work synchronously. Node.js: avoiding blocking work.

CPU work can be moved to worker_threads. These workers execute JavaScript in parallel, have separate execution environments and usually communicate through messages. Memory can also be shared explicitly. For recurring tasks, a worker pool is more appropriate than creating a worker per small request. This is not the same pool Node uses internally for certain I/O tasks. Node.js: worker threads.

Go: sequentially readable code within many goroutines

In our Go version, the form handler calls Verify and Send normally, one after the other. While a network call waits, the runtime can execute other goroutines. These calls therefore need no await. net/http provides concurrent request handling; we need no manually started goroutine around every handler.

The resulting parallelism requires memory discipline: two handlers may access the same map simultaneously. Our catalogues therefore remain unchanged after loading, while language and route stay within each request. An indexing goroutine added later could still consume enough CPU and memory to slow the website. Goroutines replace neither capacity planning nor limits on concurrent jobs.

Java: several models are common

A conventional servlet application often processes requests on pooled threads. While a platform thread waits for an external service, it cannot handle another request. The code can nevertheless remain as sequentially readable as our Go form handler. The server and its configuration determine the actual thread assignment.

Virtual threads have been a standard feature since Java 21. The JVM schedules them on operating-system threads, and supported blocking I/O operations can suspend them without occupying the carrier thread throughout the wait. In this respect, the programming style approaches Go’s. Virtual threads neither accelerate CPU calculations nor eliminate data races. Whether an application’s HTTP requests use them depends on the server and its setup. Java: virtual threads.

Reactive servers also exist, such as Spring WebFlux with non-blocking execution. Blocking work on event-loop threads has drawbacks similar to Node’s. Java therefore does not automatically mean ‘one large operating-system thread per connection’. Spring WebFlux: execution model.

The same problem in all three environments: a global language

Suppose we move request.lang into a mutable global value. In Go and a concurrent Java app, requests could overwrite one another directly. In Node, confusion can occur even without JavaScript executing in parallel:

A single event-loop thread does not prevent this logical overlap. The robust design is the same in every version: language and route belong to the request. Delivery also needs protection against duplicate processing in Node or Java. An await, a goroutine or a virtual thread is not a transaction.

How code architecture would differ

The Go app explicitly connects its components in site.New. Tests replace Now, Verify and Send with function values. Node could receive the same dependencies as functions in an object. Java could use interfaces and constructor parameters. A Spring container could create and wire them, but is not required. Our simple wiring is a project choice, not a unique property of Go.

Go and Java can check fixed data types during compilation. JavaScript needs runtime checks for input data; TypeScript can additionally check project code statically. But a TypeScript type does not prove that external JSON conforms to it. The same applies to our Go app’s open M records: language choice alone does not turn them into a validated domain ontology.

Build, runtime and delivery

Our Go build generates machine code for a particular operating system and architecture. The required Go runtime is included. A typical Node deployment combines JavaScript, dependencies and a suitable Node runtime; TypeScript or bundling steps depend on the project. In a typical JVM deployment, Java is compiled to bytecode and distributed as classes or JAR files. A compatible JVM executes it and may further compile frequently used code at runtime. Background: Oracle: HotSpot and dynamic compilation; related tools are described in Dev.java: JVM and JDK tools.

These are common delivery methods, not immutable boundaries: runtimes can be bundled, and native Java images exist. A Java web server can be packaged in an executable application; a separately installed large application server is not mandatory. Node likewise requires neither Docker nor a particular framework.

For Jackie Leven, every version would also need a clear approach to JSON, Markdown, templates and assets. Our files sit beside the binary and ship together as a release. They could remain external in a Node or Java port too. Restarts, logs, provider credentials and graceful shutdown remain operational responsibilities in every version.

What this means for this project and planned search

For the current site, Go is easy to understand chiefly because of the modest standard-library solution and clear release package. Node would make direct use of your JavaScript knowledge; Java could represent the same application with fixed domain models and a different library ecosystem. These properties imply no universal ranking for speed or memory use. That would require comparable implementations and measurements.

For future search, the architectural question is more specific: when are documents read, when is an index built, and what work may occur during a visitor request? An offline indexing job can relieve the HTTP application in all three versions. When using an external embedding service, its latency and capacity may dominate. The HTTP server’s language does not replace that design decision.
