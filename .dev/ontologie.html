1. Purpose and scope

The ontology defines the kinds of things the archive describes, how they are linked, and how each claim can be traced to its evidence. It is the shared foundation for the files in the data repository, the Postgres read model, search, and the website’s machine-readable output. New content types, such as concerts, dates or people, should be added as data without restructuring existing entries.

The requirements arise from the collection. Leven embellished his life story, so the research distinguishes his own accounts from information supported by third parties or documents, and records conflicting dates for several events side by side. The concert calendar relies mainly on website announcements, which do not prove that a performance took place. A model that recognises only facts cannot express these distinctions. The ontology therefore treats claims as statements attributed to a source that can coexist with differing statements.

Class, property and vocabulary identifiers are English. The explanatory text is also English; each concept is accompanied by its identifier when first introduced.

2. Three layers

The model separates three layers. The entity layer contains the archive’s entities: people, groups, places, events, works, recordings, releases, documents and media objects. The statement and evidence layer connects these entities with one another or with values and records the basis for each connection. The presentation layer contains the website’s editorial units, such as timeline entries, listening recommendations and the sequence of biography chapters.

Presentation units refer to entities but do not replace them. A timeline entry is an editorial selection with its own text referring to an event and a place. If the event’s date is corrected, the information changes in one place and applies to every presentation using that event.

3. Modelling principles

Events as entities in their own right

Much of what the archive records about Leven concerns events: concerts, recording sessions, interviews, broadcasts, his birth, the assault in the 1980s, moves, and deaths in the family. Events are therefore entities with a time, place and participants. People, works and places are connected through participation in events. A concert thus links Leven and his accompanying musicians to a venue, the works performed, recordings, and reports of the performance. This principle comes from the CIDOC Conceptual Reference Model (CIDOC CRM), the reference model for cultural heritage documentation.

Work, recording and release

The model distinguishes a song as a composition (work), a particular performance recorded of that song (recording), and a publication on which that recording appears (release). This distinction follows LRMoo, the successor to FRBRoo, and MusicBrainz practice. The current assignment of YouTube videos shows why it is necessary: it follows song titles rather than recordings, so every occurrence of a song shows the same videos, regardless of whether it is a studio or live version. Separate recordings allow a live video to be assigned to a recording of a particular concert.

A local model mapped to standards

Using CIDOC CRM directly as the working model would make the data files unwieldy. Even a date of birth requires several intermediate nodes. The draft therefore uses a compact model whose classes and properties map to established vocabularies: schema.org for website output, CIDOC CRM and LRMoo for a complete export, SKOS for controlled vocabularies, PROV-O for editorial provenance, and the W3C Web Annotation Data Model for mentions in texts. People, places and publications are identified through Wikidata, MusicBrainz and GeoNames (section 10).

4. Identifiers and addresses

Each entity receives an identifier of the form type/key, such as person/jackie-leven or event/2004-03-26-bonn-harmonie. The key consists of lowercase letters, digits and hyphens. It is assigned once and is never changed or reused. If part of the key later proves incorrect, such as a date, the key remains; the current values from statements are displayed instead. Readable keys make files easier to work with and repository changes easier to review.

When two entries are identified as the same thing, for example during Wikidata reconciliation, one is retained. The other receives the property replaced_by and keeps its identifier so that older references still resolve.

Addresses under /id/

Every identifier is available from the outset under https://jackieleven.com/id/ for example https://jackieleven.com/id/person/jackie-leven. This address identifies the thing itself; the pages under /de/ and /en/ describe it in a particular language and may continue to change through alias lists. The response depends on the request’s Accept header:

RequestResponse
Accept: application/ld+json200 with the entity’s description as JSON-LD
Accept: text/markdown200 with a Markdown version for AI assistants and agents
Accept: text/html, entity with its own page303 to the page in the language selected by Accept-Language
Accept: text/html, entity without its own page303 to a simple entity page generated from the read model: label, statements with evidence, and links

Responses include Vary: Accept, Accept-Language. The 303 redirect follows the Linked Data convention that an address for a thing does not directly return a document. Conversely, every website page uses <link rel="alternate" type="application/ld+json"> to link to the /id/ address and uses it in JSON-LD as @id. Because the addresses are provided from the outset, resolving them belongs to the first implementation stage; this also provides a simple presentation for entities without their own page, such as most people and places.

Names, personas and credits

Leven appears in the collection under several names. All lead to the same person, but they denote different things and are therefore modelled differently.

The birth name Alan Moffatt, its variant spelling ‘Moffat’ in individual sources, and the stage name Jackie Leven are names of the person. They appear in the list names with the name type birth_name, variant_spelling or stage_name, with dates and evidence where applicable.

Leven released work independently as John St. Field, Sir Vincent Lone and Jackie Balfour; from October 2004, Sir Vincent Lone also appeared as the support act at Leven’s own concerts. These stage names are personas, separate entities of class Persona, linked to the person through performs_as, corresponding to the ‘performs as’ relationship in MusicBrainz. A release remains attributed to the persona under which it appeared and is also associated with the person through that persona.

The participation record preserves the name exactly as printed on a release (credited_as). The 1971 compilation Take Off Your Head And Listen credits Alan Moffatt as the performer and writer of ‘Finest Hour’. The participation points to the person and preserves the printed name; no persona is needed for this.

Search, pages and exports resolve all names, personas and credits to the person. A query for John St. Field finds both the persona and the person; the person’s page lists all personas with their releases and all alternative credits.

Document identifiers and external identifiers are abbreviated in this draft’s examples.

Places

Places form a hierarchy through located_in from venue through town and region to country. Research records place names in the local language; other forms are recorded as names with a language, as for people. Coordinates and GeoNames identifiers are intended for towns, and for venues only where they can be determined reliably.

Events

Each event has a type from the vocabulary event_type, a time, usually a place, and participants with roles. Through part_of, events can be nested: a concert within a tour, a performance within a festival. The performance of a work within a concert is an event of type performance with a reference to the work; the performances within a concert form its setlist.

For concerts, whether the performance took place is recorded as a separate statement performance_status with the values announced, took_place, cancelled and unknown. An entry in a website calendar establishes only the announcement. A concert receives the value took_place only when further evidence exists, such as a photograph, report, recording or later mention in a column.

Works, recordings and releases

A work has a title and title variants, creators with their roles, a creation date where known, and references to works on which it is based. A recording uses recording_of to refer to the work recorded, has a type from the vocabulary recording_type (studio, live, demo, broadcast), and is connected through recorded_at to the event at which it was made. The 2004 Rockpalast concert thus produces one recording per song; tracks on the 2011 and 2024 releases containing that performance refer to these recordings.

Recording and release dates are separate statements. For the Doll by Doll live album Revenge of Memory , sources give 1977 or 1980 as the recording year and years between 2003 and 2006 for its release. Both conflicts are represented independently as competing statements.

A ReleaseGroup groups the editions of an album or single, such as the first issue and later reissues. Entries in the current discography that bundle several single variants are split into separate releases. A track on a release is not a separate class but a statement using the relationship tracks with qualifiers for medium (such as side A or CD 2), position, duration and printed title, which may differ from the work’s title. As a statement, it has a stable identifier and can carry evidence. Which tracks on different releases contain the same recording is researched before migration (section 13).

Documents and publications

A document has a type from the vocabulary document_type, participants with roles (author, interviewer, photographer, translator), a language and a date. Through published_in, it appears in a publication, with issue and page where applicable. Address, archive address, access and licence correspond to the current source headers.

An interview is both an event—the conversation with its date, place and participants—and a document, its publication. The event is created only if something is known about the conversation itself; the document then points to it through documents.

Media objects

Media objects are images, scans, videos and audio recordings, either local files or references to external services. They carry provenance (official or fan), rights and licence information. Through depicts, they connect to depicted people, places or events; through encodes, to a recording; and through excerpt_of, to the document from which a facsimile extract originates, with its page and image region.

Passages and mentions

Passages (Passage) are sections of a document, usually paragraphs, with an anchor on the target page. They serve as search index units, precise evidence locations and targets for mentions. A mention (Mention) links a passage to an entity and records whether the link was made manually or proposed by a machine and subsequently reviewed.

A passage receives a stable identifier of the form document/<key>#<passage>, which is not derived from paragraph order. When a paragraph is inserted, corrected or split, existing passages retain their identifiers; a replaced passage points to its successors. Document revision, position and a short quotation context are stored for reattachment, as provided by the Web Annotation Data Model’s selectors; positions alone would break with every text change. Search index segments are separate. They are generated during the build from one or more passages and refer to their identifiers (architecture draft, section 4).

Mentions are stored separately from the text (stand-off annotation, following the W3C Web Annotation Data Model). This leaves original column texts unchanged, as the project already requires for reading editions.

Vocabularies

Controlled vocabularies are maintained as SKOS concepts (Concept) with German and English labels, synonyms, broader and narrower concepts, and mappings to external vocabularies. The planned vocabularies are event_type, role, document_type, name_type, place_type, recording_type, evidence_type, link_type and topic. Roles map to MARC relator codes and MusicBrainz relationship types; document types map to the current source categories.

6. Statements and evidence

A statement (Statement) connects an entity through a property to a value or another entity. It may carry qualifiers, such as a period or role, and refers to one or more references. Each statement has a stable identifier (statement_id), through which references, reviews and other statements can point to it; the identifier is assigned at creation and retained when the content is corrected. Several statements about the same property may coexist even when they contradict one another. The model follows Wikidata’s statement model and can be mapped to CIDOC CRM class E13 Attribute Assignment, which describes such attributed claims.

A reference (Reference) points to a document, passage or media object. It can specify a location (locator: page, line, timestamp), a short verbatim extract (quote) and the extent to which it supports the statement (scope). With asserted_by, it records whose claim it conveys. A newspaper interview contains the interviewer’s statements and Leven’s own accounts, while a website synopsis is original writing about someone else’s claim; a document’s voice therefore does not by itself identify who makes a claim evidenced within it. Its evidence type adopts the research’s distinctions:

Rank and status

Rank is assigned editorially; its three values match Wikidata ranks. A preferred statement is the information the website displays; differing statements are identified as such. Deprecated statements retain their evidence because a widespread error also merits documentation. Source correction sections, such as those concerning the release year of Control, correspond to such statements.

Rank, certainty and conflict are separate attributes. Rank selects only the default display. Certainty is recorded by certainty: even a sole surviving personal account may be uncertain, and a preferred date may remain disputed. Where uncertainty remains, the website also shows it with the default value.

Conflict is derived from statements rather than entered. This depends on how many values a property can have at once: several band members or successive places of residence do not contradict one another, whereas two dates of birth do. If a single-valued property, such as an event’s time or place, has several non-deprecated statements with incompatible values and none is preferred, the information is disputed (disputed); if one is preferred, there are differing accounts (deviating). For a concert’s performance status, announced does not contradict any other value, since a concert that took place was usually also announced. Data repository validation already implements these rules.

The date of birth illustrates resolved information with differing values. A reference may support a statement only partly: Leven’s own mention of his birthday gives the day and month, but not the year.

Dependent sources

Two obituaries reproducing the same press release are not two independent confirmations. If a document demonstrably relies on another, it refers to it through derived_from (PROV-O wasDerivedFrom). Metrics for independent evidence count only references whose independence is established and report unresolved cases separately. Whether two sources are independent remains an editorial judgement; the model merely records it.

Evidence requirements

A property with a simple value is shorthand for a single normal-rank statement. This is sufficient for most properties. The schema marks properties as requiring evidence where research has found or expects contradictions: event times and places, whether concerts took place, participation, memberships, family relationships, residences and recording identity. Validation requires at least one reference for these. Information a document supplies about itself, such as title and author in its header, is evidenced by the document.

7. Dates and times

Dates follow the Extended Date/Time Format (EDTF), incorporated into ISO 8601-2. It can express uncertainty, approximation, intervals and alternatives that frequently occur in the research:

EDTFMeaningCase in the collection
1950-06-18Exact dayDate of birth
1975?UncertainYear supported by only one weak reference
1975~Approximate‘Around 1975’
[1976,1977]One of several„'76 or '77“
2004-10/2004-11IntervalMother’s death, late October or early November 2004
198XDecade‘In the eighties’
2011-22Season (summer)‘Summer 2011’
2008-10/..Open end‘From October 2008’

EDTF is an expression language, not interval arithmetic. An expression such as 1975~ does not imply a universal range such as 1973–1977, and a question mark specifies no probability. The data therefore stores only the original expression. Machine interpretation is produced during the build using documented rules: supported EDTF level, season convention, treatment of open intervals, and a fixed span for approximate dates. A set of alternatives remains a set; in [1975,1977], 1976 is not a named candidate.

Date filters therefore distinguish information definitely within a period from information that might fall within it. An outer date range can prefilter candidates; alternatives are then checked individually. Display always uses the original form so that an imprecise date does not appear more precise than its evidence supports.

Publication and archive dates are separate document properties (published, archived). Publication months are known for only some columns; where missing, the website explicitly labels the archive date. In the model these are two statements with separate evidence. Historical date, publication date and archive date also retain distinct meanings in search and filters.

The final relationship type is generic. It can connect any entities before a dedicated relationship type exists; its kind comes from the vocabulary link_type and can be extended with new entries. If a connection recurs, a dedicated relationship type with defined classes and qualifiers is introduced and existing generic links are converted. Since both forms are stored as statements, only the vocabulary changes, not the database schema. Validation reports generic links separately so that they do not silently become the norm.

9. Fiction

Pastiche chapters are documents with the property fiction: true. Validation rejects them as evidence for statements, preventing invented first-person prose from entering the model as information about Leven’s life. A link is provided in the other direction: the ‘Documented / invented’ sections at the end of each chapter identify its basis and can use based_on to refer to the relevant statements. This makes the relationship between pastiche passages and documented information machine-readable.

10. Reconciliation and approval

Reconciliation with Wikidata and MusicBrainz

For people, groups, places, organisations, releases, recordings and works, a tool searches Wikidata and MusicBrainz for candidates. Each candidate is saved in the entity’s data file with its review status: proposed, confirmed or rejected. Only confirmed identifiers appear in output as sameAs; rejected candidates remain recorded so that they are not proposed again. For larger sets, such as concert-calendar places, OpenRefine with both projects’ reconciliation services is suitable.

The MusicBrainz API requires a meaningful User-Agent and permits about one request per second. The tool respects this limit and caches responses so that subsequent reconciliation requests only new entities.

Contributing to Wikidata and MusicBrainz

Confirmed information from the project’s cataloguing is contributed to both projects. An export generates proposed edits: a QuickStatements batch for Wikidata, and a list of changes per release for MusicBrainz with sources for the edit note. Proposals are reviewed before submission through the project’s accounts; the tool does not edit either project independently.

The statement model transfers largely unchanged. Ranks match Wikidata’s; deprecated statements can remain there with a reason for deprecation (P2241), and disputed information is entered as equally ranked values with evidence. Evidence becomes references with ‘stated in’ (P248), ‘reference URL’ (P854) and retrieval date (P813). Approximate dates receive the appropriate precision and the ‘sourcing circumstances’ qualifier (P1480). Not every EDTF form has an equivalent; alternatives such as [1976,1977] are transferred as two statements.

Wikidata and MusicBrainz core data use CC0. Only structured information is contributed: dates, places, relationships, identifiers and track lists. Texts, synopses, quotations, translations and images are not transferred, including in edit notes beyond source attribution.

11. Data repository and licence

Repository separation

The data is maintained in a separate public repository, stefangrunert/jackieleven-archive on GitHub. The website repository, stefangrunert/jackieleven, contains the application and its source collection. This separation follows the layers in section 2: the data repository contains what the archive records about Leven; the website repository contains what the website makes of it. Repository visibility is a separate publication decision.

RepositoryContents
Data repositoryLinkML schema, vocabularies, entity data files, source descriptions, mentions, reconciliation status, cataloguing tasks and coverage registers, and tools for validation, import, reconciliation, table views, gap reports and export
Website repositoryCode, presentation layer with timeline entries, page texts and translations, pastiche, full third-party texts, facsimile and image files, research files, search test set, deployment

Full third-party texts belong to the website’s source collection. Leven’s columns and facsimiles appear on the website with their existing attribution; the data repository’s licence does not cover them. The data repository contains only their descriptions as documents and media objects. Passages in these documents are generated during the website build from paragraph order and receive stable anchors. References and mentions in the data repository point to these identifiers; the website build checks that they resolve.

The research files in research/ also remain part of the website’s source collection. They document investigative work, including sources, quotations, unresolved leads and findings. Their presence in the repository does not make every research note part of the website’s published presentation.

Versions and integration

The data repository publishes versions identified by date, such as 2026.11.02. Each version passes validation and produces exports: JSON-LD, a Postgres loading format (NDJSON) and RDF in Turtle. Exports are attached to the release as files with checksums rather than versioned in the repository. The schema also has its own Semantic Versioning number, because schema changes may affect processing in the website repository whereas data changes do not.

The website repository pins a data version through a lock file containing its version identifier and export checksum. The build downloads the export, verifies the checksum and processes it; raw files and LinkML are not needed there. For development, the lock file may point to a local data repository checkout. Every website release is thus tied to a data version, and a rollback restores the earlier data state too. This follows the allowlist and checksum approach already used to build releases.

A CI pipeline in the data repository checks every change using the validation in section 12.

Versions are also intended to be archived in Zenodo, CERN’s research data repository. This is planned for a later stage; Zenodo archives only versions published after integration is enabled. Through the GitHub integration, Zenodo stores a repository copy for each published version and assigns a DOI, a persistent identifier for citing that version; another DOI always points to the latest version. Copies remain available independently of GitHub. Published versions can be removed there only in exceptional circumstances. Before each release, its publication scope and rights metadata therefore need review; validation checks the machine-verifiable parts.

Licence

The proposed licence for data and original writing in the data repository is Creative Commons Attribution–NonCommercial 4.0 International (CC BY-NC 4.0). It permits non-commercial use, adaptation and redistribution with attribution. There is no Creative Commons licence that excludes commercial use while dispensing with attribution; all except CC0 require attribution. Version 4.0 licences also cover European sui generis database rights, which may apply to a structured collection alongside copyright. Individual facts such as a concert date are not protected as such; the licence concerns the collection and original writing.

Under the licence, non-commercial means use not primarily intended for commercial advantage or monetary compensation. A label incorporating the discography into a commercial product would therefore be excluded. Individual permission remains possible for borderline cases, such as a book about Leven from a commercial publisher.

The licence covers only material in which the project holds rights: structured information, schema, vocabularies and original writing such as source synopses. Verbatim source quotations, Leven’s texts and third-party images are excluded. Data files identify these components and the repository README lists the exceptions.

Contributions to Wikidata and MusicBrainz (section 10) are unaffected. The project additionally releases the information submitted there under CC0; CC BY-NC 4.0 continues to apply to the rest of the collection. For third parties, licence conditions apply only where rights exist in the material reused; individual facts and legally permitted uses are unaffected. The licence does not, however, cover substantial transfers from the collection into a CC0 project.

Because of the non-commercial condition, the collection is not Open Data under the Open Definition and is not described as such. It can nevertheless follow FAIR principles: findability, accessibility, interoperability and reusability through machine-readable metadata, rights and provenance. Validation checks the presence of rights information but cannot itself establish rights or determine whether personal information may be published.

A Creative Commons licence is unsuitable for the repository’s tools; Creative Commons itself advises against using its licences for software. The planned software licence is therefore MIT. The repository will contain two licence files, with the README assigning a licence to each directory.

12. Technical implementation

Schema in LinkML

The schema is written in LinkML, a YAML-based modelling language. One file describes classes, properties, ranges, vocabularies and mappings to external vocabularies. LinkML generators produce, among other things, JSON Schema for data validation, Pydantic classes for the Python pipeline, SQL DDL, a JSON-LD context, SHACL shapes and documentation. Schema, validation and output formats thus share a source. The generators do not support every feature equally, however. File schemas, reference integrity, domain rules and RDF export are therefore tested separately, and search tables are not created from generated SQL DDL without review.

Schema v0.2 exists in the data repository. It covers the classes used in the first cataloguing pass, statements with identifiers, rank, certainty and evidence, claim authors, dependent sources, and content-bound review metadata. Detailed works, recordings and releases, media objects, passages and mentions follow in later versions.

Data files

Each entity receives a file in the data repository under data/<type>/<key>.yaml. Source descriptions with longer original prose, such as the current files in research/quellen/, remain Markdown files with YAML front matter. Mentions are stored in a separate file per document under data/mentions/.

The same rule applies to homogeneous bulk data such as concerts. A concert may initially contain only a date, venue and calendar source, but later acquire evidence that it took place, a setlist, recordings, photographs and reports; conflicting dates may also appear. Such nested statements do not fit sensibly in one table row. A collective file per year would also depend on a date that may itself be disputed. Since concert keys begin with the date, the file listing already provides a chronological overview.

For overview and bulk editing, a tool generates tables from the files, such as all concerts in a year with date, venue, performance status and sources. An edited table can be imported back; the tool applies and validates changes in the files. The table is thus a view, not a second storage format. The concert calendar in research/10-konzertkalender.md is imported once. Thereafter a readable calendar is generated from the data rather than maintained alongside it.

Validation

Before each build, a tool checks:

  • Each file conforms to the schema;
  • All identifier references resolve, including through replaced_by;
  • Evidence exists for properties requiring it;
  • All dates parse as EDTF;
  • Both sides of each relationship have permitted classes;
  • Confirmed external identifiers are unique;
  • No evidence comes from documents with fiction: true;
  • Statement identifiers are unique;
  • There are no cycles in replaced_by, located_in and part_of;
  • Review checksums match the current content;
  • Passages match the passage registry, where available.

It also reports unconnected entities, generic links through linked_to, unconfirmed reconciliation candidates, and media objects still pointing to a work rather than a recording, without failing the build.

Read model in Postgres

Postgres stores the model as a graph in a few tables: entity, statement, reference, passage and mention. Alongside the EDTF expression, each statement contains the derived period as a daterange with a GiST index for date filtering. Hierarchies such as part_of and located_in are resolved by recursive queries. A materialised view entity_current holds each entity’s displayed values as JSON; the website, /id/ resolution and search usually read only this view. The search tables in the architecture draft build on passage.

Output

Every page and every /id/ address returns an entity description as JSON-LD using schema.org types and confirmed sameAs references. A complete RDF export with CIDOC CRM and LRMoo mappings is generated in the data repository and attached to each release. A SPARQL endpoint is not planned, but could be loaded from this export, for example using Oxigraph. For AI assistants and agents, the website also provides a search API and an MCP server that return statements with ranks and evidence (architecture draft, section 10).

Researching recordings

Current data usually does not establish whether tracks on different releases contain the same recording. This mapping is researched before discography migration rather than provisionally creating a recording per track. MusicBrainz recordings are the starting point where a release is catalogued there; MusicBrainz already represents the same recording across releases as one Recording. These mappings are checked against duration, credits, sleeve and booklet information, and label notes on reissues. Under MusicBrainz guidelines, a remaster generally counts as the same recording, while a different mix or edit counts as a separate one.

Migration proceeds release by release once its recordings are resolved; until then the website uses the current discography files. Recording identity requires evidence. Corrections or additions to MusicBrainz mappings are included in contributions (section 10). Once a recording is identified, YouTube media objects are also reassigned from works to recordings.

Deriving works from titles is not entirely automatic either. It relies on existing title normalisation, which already includes manual mappings for variant spellings.
