Ontology and search as a learning and reference project

The architecture is ambitious and fundamentally sound. Assertion logic, passage references, evaluation and release consistency need clarification before implementation. No additional infrastructure is initially required for this.

Reviewed: Ontology, Search architecture, Cataloguing. Also inspected: local nginx/deployment configuration and source presentation. Original documents unchanged.

Criteria and overall assessment

In search quality, “state of the art” means demonstrated performance on a particular task at a particular time. Selecting modern components does not establish it. A realistic goal here is a source-critical archive developed with current methods and reproducibly evaluated search. As a reference project, it becomes convincing through verifiable decisions, working edge cases and published results.

I would retain event-oriented modelling; separation of work, recording and release; evidenced assertions with competing values; stable identifiers; stand-off annotations; separation of data and presentation; PostgreSQL as a derived reading model; and hybrid search with optional reranking. Python, Go and PHP are defensible under the stated learning objective. A graph database, SPARQL endpoint or generative language model in the query path is not required for this level of quality.

The findings below distinguish corrections to concrete claims, design gaps before implementation, and recommendations for demonstrating quality. “Before import” concerns durable data decisions; “before operation” concerns public delivery.

Data model and source criticism

1 · Correction · Before import · Ontology §6

Preferred, reviewed and resolved are different properties

The rule “one preferred or one sole assertion ⇒ settled” is too strong. Even a uniquely surviving self-statement may be uncertain. An editorially preferred date may remain disputed. Several values may also be simultaneously valid, such as multiple band members or successive places of residence.

Change: Keep display rank, review status and conflict assessment separate. Determine conflicts with regard to property, cardinality, role and time. preferred selects the default display but does not alone decide certainty. Display remaining uncertainty with the default value too. This follows Wikidata's caution in distinguishing ranks from references and individual sources' correctness.

Source: Wikidata: Ranking. Acceptance: separately test a single self-statement, a preferred but disputed date, two valid band members and successive residences.

2 · Design gap · Before import · Ontology §§5–6; Search §4

Distinguish document voice from the origin of a claim

A newspaper interview contains both the interviewer's assertions and Leven's self-statements. An editorial article summary is another authored text. Deriving voice solely from the document can misattribute quotations and summaries. Two obituaries may repeat one press release and therefore do not provide two independent confirmations.

Change: Represent at least text kind, actual language and authorship or speaker per passage; record whose assertion each reference transmits. Document source dependencies through provenance relationships. The “independent references” metric must count only confirmed independence and identify unknown cases. PROV-O supplies derivation and quotation relationships but does not replace editorial judgement.

Source: W3C PROV-O. Acceptance: a Leven quotation in a press article and its German summary retain distinct text authorship but the same origin of the claim.

3 · Correction · Before RDF export · Ontology §§8, 12

Standard mappings need renewed semantic review

Official LRMoo version 1.1.1 lists F26 Recording and F29 Recording Event as deprecated specialisations; the intended parent classes are F2 Expression and F28 Expression Creation. The relationship table also puts F29, a class, in a relationship position. Export needs a model path there. The draft explicitly labels the table provisional, but it should be corrected before stabilising the schema.

Persona → E21 Person is not a semantically faithful mapping: CIDOC CRM explicitly distinguishes real people from personas. Likewise, MediaObject → E36 Visual Item is too broad for audio recordings and arbitrary files. A dedicated Persona class remains useful; its export must express bibliographic identity without asserting an additional real person.

Change: Pin target-model versions and distinguish exact equivalents, specialisations and lossy projections. Complete export must preserve assertions, qualifiers and references. Non-preferred or deprecated assertions must not simultaneously be exported as unqualified facts. A JSON-LD context alone does not perform this transformation.

Sources: LRMoo 1.1.1, change table; CIDOC CRM 7.1.3, E21 and E36. Acceptance: small reference graphs with expected triples and explicitly prohibited inferences.

4 · Design gap · Before import · Ontology §§5, 11; Search §6

Separate citable passages from search segments

The ontology promises stable anchors based on paragraph order; search architecture joins and splits paragraphs by token count. Both can change independently. Inserting a paragraph must not redirect existing evidence to another text. A text hash alone is also insufficient: correcting a spelling error should not destroy passage identity.

Change: Assign persistent IDs to citable source passages and version their mappings. Derive search segments from them, referencing one or more IDs. Document revision, position and short quotation context where needed aid reassociation. The Web Annotation Data Model describes selectors and state information and explicitly warns about positional references' fragility.

The public data repository also needs a verifiable register of permitted passage IDs for non-public full texts. The website additionally checks content and actual resolution. Such a manifest can contain IDs and checksums without publishing full text.

Source: W3C Web Annotation Data Model. Acceptance: insert, correct, split and resegment paragraphs; old references still resolve correctly or explicitly report a replaced passage.

5 · Clarification · Before temporal filters · Ontology §7

EDTF is an expression language, not a complete interval calculus

The examples are generally appropriate EDTF forms. But 1975~ does not imply a universal range such as 1973–1977. An uncertainty marker does not supply a probability either. A set of alternatives must not silently become a continuous period: in [1975,1977] 1976 would not be a listed candidate.

Change: Store the original expression separately from machine interpretation. Document supported EDTF level, season conventions, unbounded intervals and approximation rules. Search must distinguish “possibly within the period” from “definitely within it”. An outer daterange can prefilter but needs exact checking for alternatives. Historical time, publication date and archive date need distinct filter meanings.

Source: Library of Congress: EDTF. Acceptance: every form used in the draft and a non-contiguous set of alternatives.

6 · Design gap · Before import · Ontology §§6, 8–9, 12

Complete assertion identities and validation rules

Assertions are intended to be referenceable but lack explicit stable IDs in the draft. Also, the table permits based_on only for Work → Work, while pastiche needs documents linked to assertions. Track appears both as a class and a qualified Release–Recording relationship. These model choices need resolution.

Change: Define stable statement IDs, typed values and a canonical format. Normalise shorthand into it before validation. Exported subjects, predicates, objects and qualifiers must not depend solely on file context. Explicitly model relations to assertions. Bind both recording and later review to specific assertion versions.

LinkML remains a good foundation, but its generators do not cover all features equally. File schema, reference integrity, domain rules and RDF checks need separate acceptance tests, including cycles in replaced_by and place hierarchies, duplicates, required evidence and exclusion of fictional evidence. Physical search tables need not blindly follow generated SQL DDL.

Source: LinkML: generator and validator coverage. Acceptance: valid and deliberately invalid examples for every domain rule, including export and reimport.

Search and evaluation

7 · Recommendation · Before model selection · Search §§5–6, 8

Hybrid search and Qwen are plausible candidates; superiority remains unproven

Qwen3-Embedding-8B and Qwen3-Reranker-8B are currently listed by DeepInfra. The model card confirms multilingual embeddings, variable dimensions and query instructions. Its leading ranking explicitly refers to June 2025, not this archive in October 2026. The draft's latency estimates remain unmeasured.

RRF is a sensible starting point. Rejection of weighted scores should concern only uncalibrated addition: one research paper finds advantages for tuned convex combinations over RRF. This is not proof for this corpus either, but supports including a comparison candidate.

Change: Compare BM25, pure vector search, RRF and RRF with reranking. Also test calibrated score fusion and a smaller or independent multilingual embedding model where the learning objective justifies the effort. Treat 1024 dimensions as a configuration to measure. Model revision, tokeniser, pooling, instruction, normalisation, truncation and provider belong in the embedding profile and cache key; the actual complete embedded input, including its context header, is authoritative.

Sources: Qwen model card; DeepInfra Embedding; DeepInfra Reranker; Bruch et al.: Fusion Functions.

8 · Design gap · Before quality claims · Search §8

The test set needs judged passages and a separate final evaluation

Fifty queries make a good pilot. However, the example names an expected document while search ranks passages, allowing wrong paragraphs from the right document to pass unnoticed. nDCG requires relevance judgements; recall is meaningful only against a defined relevant collection or sufficiently judged candidate pool.

Change: Grade passage relevance, for example 0–3, and additionally measure document success. Pool results from all comparison systems for judgement and reassess strong new candidates. Separate development queries used for weights and thresholds from a held-out test set. For a reference project, I suggest roughly 120–200 carefully judged queries overall; that is a project choice, not a universal standard.

Publish results by language and query type, failure examples and uncertainty intervals. Assess no-answer questions separately: vector search returns neighbours even for nonsense, and RRF provides no calibrated relevance probability. Rejection or warning rules need their own tests. Evaluate the production configuration, including fallback, grouping and language selection.

Methodological references: BEIR and MMTEB demonstrate the value of diverse tasks and comparisons. The concrete test design here is a recommendation for this archive.

9 · Design gap · Before the search interface · Search §§4–5

Structured questions require a dedicated execution path

“Which documented concerts took place in Norway in 2004?” requires a complete query by location, date and occurrence status. The 50 most similar paragraphs cannot provide that. The ontology exists for this purpose, but its role in query execution is insufficiently specified.

Change: Translate entity recognition and explicit filters into structured SQL queries; use text search as a supplement. Offer historical time and publication time separately. Apply years as hard filters only with sufficiently clear intent: numbers may belong to titles or catalogue numbers. Exact names and IDs need a dedicated normalised retrieval path, supplemented by trigrams.

version: original/de/en mixes text kind with language. Separate fields for language, original/translation/summary and related versions are better. They also allow retrieval of the appropriate German summary when the decisive hit occurs only in English. Check duplicates per document and thematic diversity before final grouping.

Acceptance: complete concert list, catalogue number, identically named works, German query against English original, language versions without duplicate results. These criteria derive from the project's requirements.

10 · Clarification · Before index selection · Search §§3, 5, 13

Choose BM25 version and ANN index against concrete requirements

Both currently documented BM25 candidates require shared_preload_libraries and a server restart. Another database in the same cluster isolates neither extension loading nor shared resource use. This is therefore an operational decision too. Requirements include German/English analysis, unchanged proper names, phrases, field weighting, filters, memory and upgrade path.

Version-specific checking matters: current pg_textsearch documentation now describes phrase and expression indexes, which older summaries still list as limitations. pgvector iterative scans must be explicitly enabled and can still stop at scan limits. “Version at least 0.8” alone does not ensure complete results.

Change: Measure exact vector search first as a reference. Enable HNSW for this corpus only if measured benefits justify recall loss and memory cost. An ANN comparison may still be worthwhile for learning and documentation. Compare extensions in an isolated test cluster with pinned versions.

Sources: ParadeDB: installation; pg_textsearch: README and release notes; pgvector: iterative scans.

Operations and interfaces

11 · Correction · Before runtime implementation · Search §9

Go frees direct API requests, but not automatically the PHP results page

The described PHP page calls Go synchronously and waits for results. Its FPM worker remains occupied during that time. The argument for Go applies to API/MCP calls forwarded directly by nginx, not universally to server-rendered search pages.

Change: Retain Go for shared search logic, MCP support, bounded concurrency and the learning objective. Send instant search directly to the API. Define worker budget, cache and total deadline for HTML search; use a separate FPM pool if needed. Load tests must show ordinary pages remain reachable during concurrent slow searches.

Finding derived from the described call path; no server measurements performed.

12 · Correction · Before deployment · Search §7

Guarantee release consistency per request

Existing deployment switches the website symlink atomically. Restarting Go afterwards is a second operation. Between them, new PHP may talk to the old service; in-flight requests may still use the old state. Socket activation keeps the listener available but guarantees neither preservation of every accepted request nor consistent data versions.

Change: Invariant: every request uses a compatible tuple of website version, service version, dataset and search schema. Verify new components before switching and drain old requests deliberately. Parallel release instances or explicitly versioned requests/sockets can implement this. Health checks, failed restarts and rollback must honour the same rule.

A manifest should also record schema, pipeline, embedding and extension versions. Memory planning must include old and new indexes and temporarily two processes. Checksums protect files; reproducing external embeddings additionally requires retained vectors or a demonstrably compatible generation path.

Local reference: ops/deploy.sh. Socket semantics: systemd.socket. Acceptance: search during deployment and rollback, failed startup, timeout and an in-flight MCP request.

13 · Correction · Before public operation · Search §9

Data flows and logging are incompletely described

“DeepInfra receives only query text” is not true of the whole system. Indexing embeds archive passages; external reranking sends queries and candidate passages. Optional LLM context introduces another flow. Model pages currently state “Zero retention”; that establishes neither a processing region nor all contractual terms.

GET queries can also appear in nginx, proxy, error and CDN logs. nginx's default format includes the request line and referrer. The inspected local site configuration defines no dedicated format excluding search text; global live configuration was not checked.

Change: Document the three flows separately. Verify “no query logs” across every layer, including referrers, traces and errors. Keep only aggregate metrics; resolve the open question about storing unsuccessful queries accordingly. Document cache lifetime and provider terms.

Sources: DeepInfra: reranker inputs; nginx: logging module. Local reference: ops/nginx-site.conf.

14 · Design gap · Before public operation · Search §§5, 9–10

A public search API needs work and cost limits

Existing request/connection limits are inside the PHP location. New nginx locations for /api/, /mcp and /id/ do not inherit them from there. Per-IP limits alone also cannot cap paid model calls distributed over many addresses.

Change: Bound global concurrency and queue length, cap query/result sizes, set an overall deadline and fall back early to local search under overload. Coalesce identical concurrent embedding requests; temporarily interrupt external calls during sustained provider failures. A local daily budget supplements any provider limit. Several 800 ms stage deadlines do not create an 800 ms whole-request deadline.

For fetch allow only known archive IDs. Public MCP tools need precise output schemas, appropriate annotations and transport checks for the pinned protocol. CORS and robots.txt do not replace access limits.

Local reference: nginx locations. Protocol reference: MCP transport 2025-11-25; this version is a specific review reference, not a claim about all future versions.

15 · Update · Before client acceptance · Search §10

Express ChatGPT compatibility as a testable contract

search and fetch remain appropriate for Deep Research and Company Knowledge. Current official OpenAI documentation specifies a result schema, structured results and citable URLs. It now also describes connecting custom MCP servers through plugins, subject to account and workspace rules.

Change: Replace the blanket statement about “without developer mode” with a dated compatibility section. Name transport version, SDK version, client and actually tested access path. Machine-readable metadata and fiction: true help but do not guarantee correct interpretation by external assistants. Include voice and fiction status in returned text too, and run targeted citation and attribution tests.

Sources: OpenAI: MCP servers and search/fetch; OpenAI: connection and testing. The OpenAI Docs skill was used for this part of the original review.

Cataloguing and publication

16 · Recommendation · Before agent pilot · Cataloguing §§3, 6–7, 10

Review needs a small gold sample and versioned decisions

Document-level proposals, diff review, negative research results and spot checks form a good foundation. A human in the loop alone does not make extraction reliable. In particular, a name recorded at merge time does not prove that every subsequent assertion revision was reviewed.

Change: Start with roughly 20–30 documents of varying difficulty and create a manually judged reference set. Measure extraction accuracy, omitted assertions, false merges, misassigned references, correction effort and runtime. Bind review decisions to content and revision; semantic changes require renewed review. Jobs record input version, instructions, model, output and usage. This remains traceable without detailed internal model reasoning.

Parallel worktrees do not automatically see other jobs' new proposals. Before merging, shared reconciliation and serialised identity allocation/merging are needed. Coverage should distinguish attempted, fetched, readable, fully checked and aborted. An OCR search with no results does not prove that a name is absent from an entire magazine year.

Recommendations derived from the draft's requirements. Verifiable provenance can be described with PROV-O. Automated evaluation supplements the human gold sample.

17 · Clarification · Before publication · Ontology §11

Define licensing and public reference material precisely

CC BY-NC is a possible project choice. However, the collection should not then be advertised as Open Data under the Open Definition, which requires commercial reuse. FAIR properties such as discoverability, provenance and machine-readable metadata remain achievable.

The claim that others fundamentally cannot transfer information to Wikidata is too broad: licence conditions apply only where relevant rights exist; public-domain elements and statutory exceptions remain unaffected. Extensive copying of a protected collection is a different matter. Public archive data, excerpts and original project texts need unambiguous machine-readable rights information.

Change: Do not silently change the existing licence decision; describe its scope more precisely. CI checks recorded permissions and metadata but cannot itself establish rights or assess personal information. For public demonstration, provide a reproducible subset with suitable test data, schema, tools and evaluation report; a private test set alone is not externally inspectable.

Sources: Open Definition 2.1; FAIR principles; Creative Commons: scope and exceptions. No final legal assessment of individual archive materials was performed.

Recommended implementation and evidence

The scope can remain ambitious. Divide the first stage into verifiable end-to-end increments so ontology, search, export and operations do not simultaneously depend on one another's untested assumptions.

StepOutputAcceptance
1. Model pilotPerson, persona, place, concert, document, assertion and passage; a small set of difficult examples.Self-statements retain uncertainty; contradictions remain visible; announcements do not become occurrences; evidence anchors stay stable.
2. Reproducible importValidation, data release, passage manifest, small PostgreSQL reading model and initial /id/ responses.Identical inputs yield identical normalised exports; relationships and references resolve; invalid facts do not enter exports.
3. Search and comparisonBM25 baseline, embeddings, hybrid search, optional reranking; judged development and test sets.Improvements visible by query type; costs, memory, p50/p95 and failures documented; more than a single overall score.
4. Public operationHTML, API and MCP with version binding, limits, fallback and verified logging.Load, provider failure, deployment and rollback tested; ordinary pages stay available; marked queries absent from agreed logs.
5. Scaled cataloguingAgent jobs, review and coverage register after evaluation of the pilot.Precision, omissions, duplicates and human effort are known; changes trigger necessary re-review.

Useful later presentations include concise architecture decisions with alternatives and measurements, a publicly runnable example, a documented failure catalogue and a release report. A defensible description would be: “A source-critical knowledge graph with standards-based exports and reproducibly evaluated multilingual hybrid search.” Claim superior search quality only for comparisons actually performed.

Review limits

This is an architecture/document review using current primary sources and selective local code inspection. No search models were benchmarked, server configurations changed, live databases queried or paid API calls made. Actual latency, available memory, installed extensions, Cloudflare rules, global logs and specific account/contract terms remain open. Collection counts in the drafts were not remeasured.

Recommendations are distinguished from existing project decisions. Data licences, provider choice, publication approvals and final technology choices were unchanged. Web sources were accessed on 25 October 2026; product documentation and repository main branches may change afterwards. Pin concrete releases before implementation.
