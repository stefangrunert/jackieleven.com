1. Starting point

The jackieleven.com website currently contains 73 columns by Jackie Leven totalling around 90,000 words, 741 sources about him from 1971 to the present, 88 discography entries with 881 track entries, timeline stations and 15 chapters of an autobiography labelled as pastiche. Research includes further material not yet on the website, including a calendar of 470 performances. More press articles, dates, concerts and people are to be added.

The texts are bilingual but not parallel: columns and many quotations exist only in the English original, while source synopses are in German and English. Proper names, album titles and years are frequent. No search function exists yet; content is accessible only through timelines, lists and filters.

The website, including its form, has run on Go since 25 October 2026. cmd/jackieleven starts a net/http server; internal/site contains routing, content preparation and html/template templates. JSON catalogues and columns load at startup. Search, Postgres integration, /id/ resolution and MCP are not implemented yet. The code currently uses only the Go standard library. This inventory refers to commit d819f9d; all search components below are plans.

According to the documented infrastructure state, the website shares a server with 2 vCPUs and just under 4 GB RAM with other services; Postgres 17 is available. PHP remains only as a fallback for the former application. The Go migration adds neither CPU nor memory. Hosting a large embedding model is therefore still not the intended production solution; model size and response time need measurement.

Agreed structure

Website and search will be developed as two Go programs in the same code repository. The website renders pages and handles the form. A separate search service handles search, evidence resolution, the public JSON API and later MCP. The server-rendered results page calls it through an internal HTTP API. Separation allows independent restarts, targeted resource limits and later reuse of the search technology.

Connection, CPU and memory budgets and load tests are therefore required. All new program paths, endpoints and configuration names in this draft are implementation proposals.

2. Requirements

Search should answer queries by meaning, across languages. A German query about Leven’s alcohol dependence should find English column paragraphs that do not use that term. It must also match names, titles, catalogue numbers and years precisely and tolerate name variants.

Results are passages, usually paragraphs, linking to their location on the target page. The project distinguishes Leven’s own writing, third-party accounts, documented data and the invented autobiography; results preserve those distinctions.

Search is also accessible to AI assistants and agents. An assistant searching the web during a conversation, such as ChatGPT, should be able to find, retrieve and cite archive pages with precise locations; an agent with its own tools should query search directly (section 10).

New content types are added as data without architectural changes. Changes to models, weighting or segmentation are measured against a fixed test set. Search queries are not logged. If an external service fails, search continues with reduced quality. An ordinary form keeps it usable without JavaScript.

3. Data storage and collection status

Structured data lives in the separate public repository stefangrunert/jackieleven-archive. Website and search code, presentation and full third-party texts remain in the website repository (ontology, section 11). It is never edited manually and can be rebuilt from pinned inputs; external embeddings are additionally retained as build artefacts.

How the collection is assembled

  1. Define the job – jobs/ defines source scope, entity classes, method and budget.
  2. Evaluate sources – find and extend existing entities; record new entities as data/<type>/<key>.yaml files.
  3. Support statements with evidence – retain stable statement IDs, source, location, verbatim quotation where applicable, evidence type and uncertainty; distinguish announcement from occurrence.
  4. Document coverage – coverage/ records reviewed material, findings, inaccessible sources and references that were only counted.
  5. Validate and review – check schema, references, identifiers, evidence, duplicate notices and conflicts; correct before merging into main.
  6. Derive a search snapshot – later, a versioned export, passage registry, segments and Postgres import; no direct search over continuously changing working files.

4. Data model and index unit

The data model is described in Archive ontology. Three parts matter for search. Entities are the archive’s subjects: people, groups, places, events such as concerts, works, recordings, releases and documents. Statements connect entities to one another or to values and carry evidence. Passages are citable document sections with stable identifiers and target-page anchors; references and mentions point to them. Search instead indexes segments generated during the build from one or more passages and referring to their identifiers. Search segmentation can then change without making a reference point to different text. Schema and database identifiers are English.

Every passage belongs to a document. The historical source’s voice (source_voice) is separate from the voice of the actual indexed text (text_voice): an editorial synopsis of someone else’s concert review remains editorial text; a verbatim extract carries its original author’s voice. The same applies to Leven’s texts and pastiche. Results are initially grouped by actual text voice; source voice and text kind remain visible. An additional source-voice filter does not change attribution. Editorial summaries must not appear as original quotations. Mentions connect passages to entities. If search recognises a place or person in a query, it can therefore show the entity and its relationships alongside passages.

Each search segment receives these fields:

5. Search request flow

Lexical and semantic search complement one another in this collection. Vector search matches names, catalogue numbers and years unreliably because rare strings are only imprecisely represented in vectors. Word search cannot find paraphrases or texts in another language. Both therefore run in parallel, and their ranked lists are fused.

  1. Query analysis – Known names and identifiers are recognised through a normalised name path, supplemented by trigram matching for variants. Birth names, spelling variants and personas resolve to the person: ‘Sir Vincent Lone’ identifies both persona and person. Years become hard date filters only with clear intent, since a number may be part of a title or catalogue number. A structured question follows the structured path below. The method is deterministic and requires no language model.
  2. Lexical search – Field-weighted BM25 over text, titles and names. In parallel: Semantic search – Query vector through DeepInfra (cached), vector search with pgvector.
  3. Fusion – Reciprocal Rank Fusion of both ranked lists in the Go search module, using the same filters and data snapshot.
  4. Reranking – Rescore the best 50 results with a cross-encoder, only on the full results page.
  5. Presentation – Group by voice, show entities for recognised names, link to passages.

Fig. 2: Request processing steps

Fusing ranked lists

Reciprocal Rank Fusion combines ranks, not scores. BM25 values and cosine distances use different scales. The constant 60 and candidate count 50 are starting points for the test set, not optimised values. A calibrated combination of normalised scores remains a planned comparison.

The database returns two ordered candidate lists from the same immutable search schema. The Go layer merges them by segment ID and can retain the lexical list if the vector path fails. Local search therefore need not wait for external embedding. SQL-based fusion remains a later alternative to measure. Queries use the separate language and text-kind fields from section 4.

# Flow sketch, not existing executable code
lexical := BM25(query, filters, boundSchema)     # start immediately
semantic := VectorSearch(Embed(query), filters, boundSchema)

# Both paths have sub-deadlines within an overall deadline.
# If the optional semantic path fails, lexical remains available.
score(segment) = sum(1 / (60 + rank_in_list))
# One contribution per segment per list; ranks start at 1.
# Break ties deterministically by segment ID.

Query language, original language, text_kind and version_group remain separate attributes. Cross-language candidates must not be prematurely excluded by a hard interface-language filter. After ranking, a suitable translation or synopsis from the same version group is displayed where available. Document, date, voice and visibility filters apply consistently to both paths; display alternatives must also satisfy them.

Multiple segments and language versions of one document are consolidated before final display. The response retains concrete passage IDs as citation targets. Fallback operation is identified through mode and a factual limitation; database errors are not presented as ‘no results’.

Structured queries

‘Which documented concerts took place in Norway in 2004?’ requires a complete list by place, date and performance status. A ranking of similar paragraphs cannot provide that. When query analysis recognises entities and unambiguous filters, the search module translates them into a structured query over read-model statements, for example concert events located in Norway, dated in 2004 and with status took_place. Text search supplements the result with relevant passages. Historical time and publication time are separate filters.

Vector index

Exact vector search without an approximate index provides the reference for candidate-retrieval recall; its latency for the actual segment collection must be measured. Complete recall for this distance search does not mean every relevant piece of evidence appears among the top results. An HNSW index is introduced only if measurements justify its speed gain against recall loss and memory use; the comparison may still be conducted and documented for learning. Filtered HNSW queries may return fewer results than requested. pgvector can continue searching only if iterative scans are explicitly enabled, and even then stops at a scan limit.

When a sub-deadline expires, its optional step is skipped. Without a query vector, BM25 and name matching remain; without reranking, the previous order stands. The lexical query starts alongside vector generation with a reserved budget. Pool, SQL and provider deadlines derive from the request context. External calls end before the overall deadline to leave rendering time. External-path overload falls back early to local ranking; if local capacity is also exhausted, requests are rejected within bounds rather than queued indefinitely. ‘Local’ means Postgres search without provider calls. If Postgres fails, search paths return a controlled 503; existing content pages remain available from files.

6. Embeddings

The planned model is Qwen3-Embedding-8B through DeepInfra’s API, which also offers Qwen3-Reranker-8B. The choice is based on experiments in other projects. The model card’s leading benchmark position refers to June 2025 and general benchmarks; it establishes nothing for this archive. The test set will therefore compare the smaller 0.6B and 4B variants and an independent multilingual model. Model weights are published. If the provider disappears, the same model can run elsewhere or on owned hardware and the collection can be embedded again.

The model produces 4,096-dimensional vectors. Matryoshka Representation Learning concentrates most information in the leading dimensions. Vectors are truncated to 1,024 dimensions and renormalised. Stored as halfvec, each vector occupies 2 KB, or about 200 MB for 100,000 segments, plus table and index overhead. The test set determines whether 1,024 dimensions suffice.

Index and query must use the same model at the same precision. Locally generated vectors, such as from a quantised Ollama version, are not interchangeable with provider vectors.

For the planned DeepInfra Qwen3 embeddings, a local API key is stored in .dev/deepinfra-api-key. The file is untracked, Git-ignored and excluded from the release allowlist, with owner-only permissions. The future pipeline or search service reads it at startup into JACKIE_DEEPINFRA_API_KEY without logging it. Storing the file alone enables no provider calls; integration remains to be implemented.

Segment boundaries

Segments follow document structure: paragraphs of roughly 150–400 tokens, never crossing document boundaries. Short paragraphs are combined with neighbours; long ones are split at sentence boundaries. Track lists and quotations remain intact.

Context header as a comparison variant

The first implemented baseline qwen3-8b-1024-v1 embeds only the stored text. The context variant below remains a comparison to measure and is not part of this profile. Documents are currently imported paragraph by paragraph with at most 2,400 characters per passage.

A column paragraph usually names neither author nor date. One proposed variant therefore prepends a header from document metadata:

Jackie Leven · The Deep Pool · Column, March 2005
[Paragraph]

Sounds · 6 November 1971 · Jerry Gilbert · Review
[Paragraph]

A language model may additionally generate one sentence per passage situating it within the document (Contextual Retrieval). That sentence is cached; any improvement in retrieval quality is measured.

Query instruction

Qwen3 embeds queries with a prepended task description and documents without one. The description is tailored to the collection and written in English, as recommended by the model documentation:

Instruct: Given a question about the Scottish songwriter Jackie Leven,
retrieve passages from his own writing, press coverage, concert history
and discography that answer it
Query: Wann war Jackie in Norwegen?

Cache

Vectors are stored under an embedding profile: model and revision, tokenizer, pooling, query instruction, normalisation, truncation and provider. The cache key combines that profile with the complete embedded text, including any context header. A build embeds only segments lacking a matching validated artefact. This persistent build cache is separate from the search service’s short-lived query cache; its registry and resumption are described in section 7. Recording the profile on the build makes model comparison a build parameter. Release vectors are retained because external embeddings cannot reliably be regenerated identically.

7. Build and deployment

  1. Pin inputs – Record website content, archive export, passage registry and checksums.
  2. Prepare search snapshot – Generate segments and profile-bound embeddings; load an immutable membership list under a build_id into schema search.
  3. Build programs – Separate binaries and packages for website and search service, with compatible API contracts and manifests.
  4. Verify – Test evaluation, readiness, data binding and interaction between both programs.
  5. Activate – Provide the matching search service; bind the website and public search routes to the same approved content snapshot.
  6. Accept or roll back – Check errors, link targets and fallback; restore a compatible previous combination.

Fig. 3: Planned release flow for two programs. The current packager builds only the website.

Import, segmentation, batch embeddings and evaluation remain Python tools managed with uv, outside both runtime processes. The existing Go packager and allowlist are extended deliberately or supplemented with a search-service package. build.json currently contains only revision, dirty status and target platform. Search manifest, API version and published-passage binding are new. Database credentials and provider keys stay outside packages.

Persistent indexing state and continuous data growth

The collection grows continuously. The pipeline therefore needs persistent work state that survives process restarts, interrupted runs and new releases. A ‘last indexed’ timestamp is insufficient: changes may affect texts, evidence, filters, target URLs or model profiles, and removed content must also be detected. Git retains source history; the indexing registry retains processing state. The approved index remains immutable until the next verified switch.

A separate management schema is implemented: indexer_state in Postgres, separate from shared read tables in search. Each published membership list remains immutable under its build_id; all queries are bound to it. Only the pipeline has write access there. The search service needs no write access to this registry. Durable operational state also includes the embedding artefact store and release manifests, outside Git and replaceable program directories. This infrastructure exists locally; production operation is not approved yet.

Git diffs may accelerate work later but do not replace reconciliation for missing or removed records. File modification times are unreliable. The pipeline tracks dependencies too: changes to a person’s name, statement or publication metadata require derived names, filters or context headers to be recalculated even if the document’s source file is unchanged. Only then does the relevant hash determine whether a new embedding is needed. This handles ongoing growth correctly without sending every text to DeepInfra again as a precaution.

Interrupt, resume and approve

Work steps have explicit states such as pending, running, done and failed. A run can pause: it accepts no new work and saves results already received. After a crash, expired leases become available again. One active writer per project suffices initially; transactions, unique work keys and renewed lease tokens prevent conflicting completions. External network calls do not hold long database transactions open.

A returned embedding is checked for dimensions and valid numbers, persisted, then marked complete. Repeating local work is idempotent. If a connection fails after successful provider processing, another paid call may still be needed; no exactly-once guarantee is made without confirmed provider support. Bounded retries with increasing delays, a cost budget and visible failure states prevent endless loops. The registry contains archive processing data, not visitor query logs.

Incremental processing is compatible with complete release snapshots: a new build contains every approved document, reuses unchanged artefacts and adds only changes. PostgreSQL indexes may initially be rebuilt fully in the new schema. The first optimisation concerns expensive embedding calls and repeatable preparation, not necessarily every local index operation. A build can be approved only once all intended elements and references have been checked. Failures leave the previous snapshot active; an intentionally reduced selection requires a new explicit input manifest.

New approved archive versions may trigger the next run; trigger and schedule are implementation decisions. Source changes alone do not switch a public index. Data approval, website content and search approval stay aligned under the version contract below. An older run finishing later must not displace a newer approved state.

Backup and recovery cover registry, artefacts and referenced manifests. Cleanup follows their references: active builds, resumable runs and permitted rollbacks retain their artefacts. Required content removal also entails checking stored text, vectors, caches and allowed rollbacks; rollback must not republish removed content.

Separate programs, matching data

Three identifiers serve different purposes: data_version identifies the archive export; content_version identifies the approved content snapshot including website texts, passage IDs and target URLs; search_release identifies search-service code and index configuration. An archive commit alone is insufficient because texts and anchors may change in the website repository. The exact calculation of content_version is defined in the import contract.

At startup, the website reads its expected content version and internal search address from approved configuration. The search service binds exactly one immutable build membership list, embedding profile and content manifest. The website sends its expected content_version with every internal request; the service explicitly rejects mismatches. The website also checks the response’s version. HTTP 200 carrying a different data snapshot is not displayed as a valid result.

A search-code or ranking-only update can ship independently if API and content version remain compatible and evaluation passes. Changed content or anchors require coordinated approval. Initially, a short controlled search interruption is acceptable: block search entry points, start and verify the new combination, then reopen public routes. Existing file-based pages remain independent of search. The current website restart itself may briefly interrupt service; an atomic symlink switch alone does not make the whole deployment uninterrupted.

A later switch with overlapping instances starts the new search service on a separate loopback endpoint. Old website instances retain their fixed old endpoint; new ones use the new endpoint. Public JSON, ID and MCP routes switch only after target-page checks. Already-open search forms also bind their content version; outdated requests receive a clear reload instruction rather than silently mismatched results. Multi-step API/MCP flows such as search and fetch must also bind the same content snapshot or explicitly abort on a switch. This procedure and its temporarily doubled resource use must be tested before implementation.

Readiness, rollback and permissions

Search-service readiness checks API compatibility, data revision, schema format, index readiness and embedding profile. Release approval combines this with the website’s content version. The external embedding provider is not required for readiness because lexical fallback must work. A later search-process or Postgres failure affects search and data-dependent entity pages; ordinary pages and the form do not depend on them.

Website and search service receive separate systemd units and users. Only the search service gets a read-only database role and provider keys; the website needs neither. A separate build/deploy role creates schemas and indexes. Schema names come only from validated configuration and are quoted correctly as SQL identifiers; request parameters cannot select roles or schemas. SQL values are parameterised.

Rollback restores a verified combination of website, search service, content and schema; compatible search-code updates can be reverted alone. Old packages and schemas remain while referenced by a running process or approved rollback. Postgres extension upgrades are separate operations and cannot be undone by switching schemas. Degradation beyond evaluation tolerance blocks approval. Failure and rollback tests include internal API and public search paths.

8. Evaluation

The test set lives in the website repository. It starts with roughly 50 pilot queries and should grow to around 120–200 carefully judged queries for credible reporting; that number is a project choice, not a general standard. It is divided into a development set for tuning weights and thresholds and a held-out test set. Passage relevance is graded 0–3; document-level success is measured separately.

- query: Wann war Jackie in Norwegen?
  language: de
  kind: cross_lingual
  expected:
    - document/1998-03-06-nordlys-live-med-leven

Queries cover exact titles and names, catalogue numbers, years and intervals, paraphrases, German queries over English texts, structured entity questions, and questions the archive cannot answer. The last group is assessed separately: vector search finds neighbours even for nonsensical questions, and RRF is not a relevance probability. Rules for flagging or rejecting weak matches require their own tests. Results from all compared configurations are pooled for judgement, with new strong candidates assessed afterwards.

Measurements also compare model size, dimensions and context-header variants. Evaluation calls the search service through its versioned HTTP API, measuring the deployed configuration including fallback, grouping and language selection. Further checks include deterministic module tests with substitute embedding/reranking functions, integration tests against isolated Postgres, website-client/service contract tests, and end-to-end tests that HTML, API and MCP use the same filters, passages and voices. Equality means matching search semantics; different interface budgets, such as instant search without reranking, are explicitly tested. Reports break results down by language and query type, with uncertainty intervals and failure examples rather than one overall score. Improved quality is claimed only for measured comparisons. A publicly reproducible subset with test data, schema, tools and evaluation report is planned so that the evidence can be checked independently.

Reusable core and archive rules

internal/search contains transferable search technology: candidate retrieval, fusion, reranking, provider access, caches, deadlines and operational metrics. An import contract brings together document IDs, text, language, metadata, passages and approved target URLs. Data import, ontology queries, filters, voices and pastiche rules remain specific to Jackie Leven. Another project needs its own adapters, configuration and judged test set.

Website and search initially share a code repository; the data repository stays separate. A second use case may justify extracting the search core into its own repository. A universal plugin system is unnecessary now. Reuse begins with a separate service instance and dataset per project; a shared multi-tenant service with permissions and quotas is an additional development stage.

Resources and failures

The search service gets its own systemd user, unit and measured CPU, memory and concurrency limits. The website retains its process and form credentials. Search restart or memory termination therefore does not terminate the website. Both still share the host, and a shared Postgres cluster remains a shared bottleneck. Process separation replaces neither SQL connection budgets nor load tests.

SQL access is planned through pgx, a bounded pgxpool and pgvector-go. Vector codecs are configured for every new pool connection. Search concurrency, pool waits, SQL execution, external calls and candidate counts are bounded. Caches are concurrency-safe and limited by size and lifetime; keys include data snapshot, query, language, filters and search profile. Coalesced concurrent provider requests have their own bounded budget independent of any one waiting client. Cost limits must account for all active service instances together.

Drivers and SDKs are pinned by version and go.sum; both programs must still build for Linux and be tested separately. The existing non-CGO build is checked against new dependencies. Integration tests start both HTTP processes and cover connection refusal, late or invalid responses, wrong content versions, client cancellation and nginx interaction. Ordinary pages and the form must remain accessible under search load.

Local development

The existing persistent setup remains: https://jackieleven.localhost → MAMP Apache → website on 127.0.0.1:8080, started by the LaunchAgent. ./ops/go-local.sh restart currently builds and starts only the website. Instructions are in the Go tutorial and GO-LOKAL.md.

New setup requires a search process on a separate free loopback port, such as 8081, an isolated Postgres test cluster and the search address in website configuration. The internal call suffices for HTML results; instant search, /id/ and MCP also need suitable MAMP proxy routes. A separate startup/build script and optionally a second LaunchAgent allow independent restarts. This setup does not exist yet; current operating scripts do not automatically control the new service.

Small publishable fixtures, versioned SQL and an import command make setup reproducible. Paid provider calls are disabled locally by default; substitute functions support tests. A container or dedicated cluster with pinned extensions avoids modifying other local databases. Another database in the same cluster does not provide this isolation.

Privacy

Three planned data flows go to DeepInfra: archive segments during build, query texts for query embedding, and query plus candidate passages for reranking. The service sends neither visitor IP addresses nor cookies. An optional model-generated context sentence would add a fourth flow. Processing region, retention and contractual terms are checked against the provider’s then-current documentation before release; architecture alone guarantees no deletion. The website’s privacy section must describe every enabled flow.

Search texts are not logged. Aggregate operational metrics cover latency, load, errors, fallback and no-result rates; query text, IP addresses and document IDs are not metric labels. Query vectors and results may exist only in bounded, short-lived internal caches. The proposed key JACKIE_DEEPINFRA_API_KEY and database credentials belong in the new service unit’s protected environment file, proposed as /etc/jackieleven/search.env, outside repository, release and manifest. The key is never returned to browsers or MCP clients. Local and provider-side spending limits complement one another.

GET search text may appear in access logs, error output and referrers. The Go nginx template currently defines no dedicated access-log format; inherited server and Cloudflare settings must be checked. Search paths need logs without query strings and a consistent Referrer-Policy: no-referrer; the current strict-origin-when-cross-origin passes the full URL for same-origin requests. Go and proxy must not set contradictory duplicate headers. Search responses receive Cache-Control: no-store and HTML results additionally receive noindex. Errors and traces contain no query text. A marked test string checks all agreed logs, including local MAMP. The GET URL remains visible in the browser and may appear in its history; this is distinct from server-side logging.

10. Access for agents and AI search

AI assistants reach the archive in two ways. Web search finds pages through an index, retrieves them and cites them; pages must therefore be accessible, machine-readable and clearly labelled. Agents with their own tools query search directly through HTTP or MCP. Both routes use the same search and read model as the website.

Crawlers and retrieval

OpenAI distinguishes three crawlers treated separately in robots.txt: OAI-SearchBot builds ChatGPT’s search index, ChatGPT-User retrieves pages at a user’s request, and GPTBot collects training content. According to OpenAI, robots.txt rules may not apply to ChatGPT-User because retrieval is user-initiated. Anthropic similarly distinguishes Claude-SearchBot, Claude-User and ClaudeBot.

The website’s robots.txt currently permits all crawlers. That does not ensure access: Cloudflare can independently block or challenge AI crawlers, reportedly with such defaults for new domains. Zone settings therefore need checking, with search and retrieval crawlers explicitly permitted. Any Cloudflare-managed rules prepended to robots.txt are disabled or aligned with the rules below.

Training

Training crawlers are permitted, including for Leven’s columns. The columns are already accessible through the Internet Archive and probably present in earlier web-text collections; blocking them on this website would change little about that. The website reproduces them without explicit permission from the rights holders and promises on its About page to remove them promptly on request. Such a request would remove the columns from the website and block their paths for training crawlers; material already used in training cannot thereby be withdrawn.

Facsimiles are excluded because they reproduce extracts from newspapers and records for which the project holds no rights. Search, API and MCP endpoints are also excluded: their query-dependent answers duplicate page content and each uncached request may incur a paid DeepInfra embedding call.

robots.txt is currently generated by the Go router in internal/site/server.go. This handler will gain a group for known training crawlers; local and prefixed previews retain indexing protection. A crawler follows only its named group, so the training group contains all rules applicable to it.

Search and retrieval crawlers such as OAI-SearchBot, ChatGPT-User, Claude-SearchBot and Claude-User fall under the first group. They may read pages and use them for answers, corresponding to ai-input=yes. No ai-train signal is set because it would apply to every path in the group and cannot express the facsimile exception. Google-Extended controls use by Google’s AI models, not Google Search indexing.

robots.txt is voluntary and does not stop non-compliant crawlers. If needed, Cloudflare firewall rules can additionally protect excluded paths from known training crawlers. The list is not exhaustive and can be extended.

The existing five-requests-per-second limit applies per IP address. Assistant retrievals arrive through a few provider address ranges and may hit this limit even if each user requests only one page. The draft therefore proposes higher limits for OpenAI’s published per-crawler JSON IP lists. Some AI searches also rely on conventional indexes; changed URLs are additionally reported through IndexNow after deployment.

Machine-readable pages

All pages are server-rendered and fully readable without JavaScript; the website already meets that prerequisite. Additions include:

  • JSON-LD on every page with the /id/ address as @id, type, date, creator, voice and confirmed sameAs references.
  • Voice labelling in visible text and JSON-LD. Pastiche chapters also receive machine-readable fiction labels so assistants do not quote them as Leven’s words.
  • An anchor per passage. Each passage is citable through a fragment URL; search, API and MCP results point to those URLs.
  • Markdown representation of every page and every /id/ address through Accept: text/markdown: main content without navigation, with a header containing title, date, creator, voice, canonical URL and licence.
  • llms.txt at the root, briefly describing the archive, voice distinctions, main sections, API, MCP server and data repository. This follows a proposal, not a standard; assistant adoption is uncertain, while implementation effort is small.
  • Search page with a GET URL. /de/suche?q=… returns server-rendered results so an assistant capable only of fetching pages can use search. Result pages carry noindex but remain accessible to search and retrieval crawlers, excluding the training crawlers listed above.

HTTP API

The planned API is read-only and keyless. Same-origin instant search needs no CORS. The deliberately public JSON endpoint gets an explicit CORS policy without cookies or other credentials. This does not permit arbitrary MCP origins. An OpenAPI description is published at /api/openapi.json.

GET /api/search?q=Norwegen&lang=de&type=document&from=1990&to=1999&limit=20

The response contains query interpretation (recognised entities and date filters) and, per result, passage ID, anchored URL, document title and date, voice, snippet and licence. Recognised entities include their /id/ addresses, where statements, ranks and evidence can be retrieved as JSON-LD.

Limits for API and MCP

In the current Go template ops/nginx-go-site.conf, request and connection limits are in location /. New paths such as /api/, /mcp and /id/ initially fall into this block. Dedicated locations must explicitly retain or appropriately configure limits, proxy parameters and security rules. Targeted forwarding is planned for /api/search, approved API descriptions, /mcp and /id/ to the search service; ordinary pages and HTML search remain with the website. Public search maps deliberately to the versioned service path. Public readiness or administration access is not enabled. Per-IP limits alone cannot bound paid requests distributed across many addresses. The search module therefore caps concurrency, queue length, request/result sizes and the overall deadline from section 5. Identical concurrent DeepInfra requests are coalesced; persistent provider errors temporarily suspend external calls. A local daily call budget supplements the provider spending limit. fetch accepts only known archive IDs. CORS and robots.txt replace none of these limits.

MCP server

An MCP server at /mcp provides read-only search through Streamable HTTP without sign-in. The implemented protocol version is pinned alongside the official Go SDK version and tested against intended clients. Earlier planning named 2025-11-25; the SDK now also documents 2026-07-28. Tested version negotiation is decisive, alongside origin checks, precise output schemas and read-only tool annotations. For Deep Research and ChatGPT knowledge integration, OpenAI describes two tools named search and fetch with defined result schemas, structured output and citable URLs. The server provides both in that form: search returns IDs, titles and URLs for passages and entities; fetch returns full content with metadata and evidence. For agents using additional tools, it also provides get_entity (statements with ranks and evidence), list_events (by period, type and place) and list_disputed (disputed information). Claude and other MCP clients use the same server.

Transport needs its own operational checks: the existing website sets WriteTimeout to 45 seconds, and nginx read/write timeouts to 35 seconds. The new search service has separate HTTP deadlines; MCP runs there and need not inherit website deadlines. Normal search calls stay well below them. Streamed MCP responses additionally require checks for proxy buffering, cancellation and potentially longer connections; if needed, adjusted deadlines and proxy_buffering off apply specifically to this transport. Other website timeouts are not removed wholesale. Short bounded tool calls suffice initially; permanently open sessions are not a goal in themselves.

Connecting custom MCP servers to ChatGPT depends on account, workspace and OpenAI’s current rules, which have changed repeatedly. Compatibility is therefore recorded as dated evidence: protocol, SDK version, client and access actually tested.

API and MCP return voice, evidence type, rank and references for every statement. An assistant can distinguish Leven’s own accounts from third-party information and present disputed dates as disputed rather than choosing one value. When reading pages, it would have to infer these distinctions from prose.

API and MCP requests are handled like website searches: query text goes to DeepInfra for embedding and is not logged. Machine-readable metadata and fiction: true improve the conditions for correct reporting but do not guarantee it. Voice and fiction status therefore also appear in returned text, with targeted tests for citations and misattribution.

Verification

The section 8 test set is supplemented with assistant tasks: questions to ChatGPT and Claude using web search and connected MCP. Checks cover whether the archive is found and cited at the right passage, disputed information stays disputed, and pastiche is not used as evidence. These checks are repeated manually at fixed intervals because assistant answers cannot be automated reproducibly. Aggregate Cloudflare bot statistics show crawler access.

An additional ready-made platform such as Elasticsearch remains outside the plan; our Go search service uses Postgres. Postgres suits a relational read model of statements and evidence and can manage text and vectors together. A relational database is a project choice, not an inherent requirement of an ontology. The Go migration alone does not justify replacing the evaluated storage and retrieval design.

If extension installation proves difficult, a serious alternative is an embedded Go index such as Bleve, which supports text, vector and hybrid search. Bleve would run inside the search service without another search platform. Reproducible index files, language processing, memory limits and relationships would still need work. Bleve was also possible with the previously planned Go service; migration does not automatically make it superior. It remains a comparison option if Postgres extensions impose excessive operational or resource demands in the isolated pilot.

According to their installation instructions, both BM25 candidates require inclusion in shared_preload_libraries and a cluster restart: ParadeDB pg_search and pg_textsearch. Changing the website language does not alter that. Exact and approximate vector retrieval are assessed against pgvector behaviour, not estimated from the small number of visible pages.

Generated answers at runtime remain outside the first stage. Their quality depends on underlying retrieval, which must be measured first. Embedding and reranking are separate model tasks.

13. Open questions

Decisions needed

  • Pastiche in search: a separate labelled group or excluded.
  • BM25 extension: ParadeDB pg_search (AGPL) or pg_textsearch.
  • Dedicated archive Postgres cluster or restart of the shared cluster: both BM25 extensions require shared_preload_libraries; another database in the same cluster isolates neither this integration nor resource use. Compare pinned versions first in an isolated test cluster: German/English analysis, unchanged proper names, phrases, field weighting, filters, memory and upgrade path.
  • No-result counts are aggregate only. Saving query texts later to identify archive gaps would deliberately change the current privacy design and is not planned here.

Check before implementation

  • Server pgvector version and iterative-scan behaviour.
  • BM25 extension installation on Postgres 17 without affecting other databases.
  • Budget separate Go-service users, units, free loopback ports, CPU/memory limits, SQL pool and caches; measure ordinary pages and form under search load and search-process termination.
  • DeepInfra latency from the server, processing region and contractual retention terms.
  • Check nginx, Cloudflare, local MAMP and Go errors for query text; inspect inherited log formats and referrer headers.
  • Memory for indexes and caches in shared Postgres; retention of multiple build membership lists during deployment and rollback.
  • Go dependencies, vector codecs and Linux builds without CGO; race and cancellation tests for shared caches and concurrent requests.
  • Set up separate packages, launch scripts and installers plus the content-version contract; repository presence alone must not publish new files. Local and production clusters need compatible pinned extensions.
  • Set up persistent indexing registry, artefact store, backup and resumption; define dependencies and hash rules. Test growth, deletion, model changes and crashes in the pilot.
  • Build passage registry and export contract; select the first search corpus and its size. The 250 document entities are not yet 250 fully segmented search texts.

  • Dated evidence for connecting MCP to ChatGPT and Claude: protocol, SDK, client and access.
